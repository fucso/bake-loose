# コメント分類ガイド

レビューコメントを適切に分類し、効率的に対応するためのガイド。

---

## 分類カテゴリ

### 🔴 必須修正

レビュアーが明確に修正を要求しているコメント。

**識別パターン:**
- 「〜してください」「〜が必要です」「〜すべきです」
- 「〜は間違いです」「〜はバグです」
- 「〜に変更してください」
- Request Changes のレビューに含まれるコメント

**対応:**
- 原則として修正を実施
- 方針が不明な場合はユーザーに確認

**例:**
> `from_raw()` は Repository 層専用なので、Action 層では mutation メソッドを使用してください。

---

### 🟡 質問

レビュアーが理解を求めている、または確認を取りたいコメント。

**識別パターン:**
- 「〜ですか？」「〜でしょうか？」
- 「なぜ〜」「どうして〜」
- 「〜について教えてください」
- 「〜の意図は？」

**対応:**
- コードベースを調査して回答を作成
- 回答内容をユーザーに確認
- 必要に応じて PR にコメントとして投稿

**例:**
> この処理で `unwrap()` を使用しているのはなぜですか？パニックの可能性はありませんか？

---

### 🟢 提案

レビュアーが改善案を提示しているが、必須ではないコメント。

**識別パターン:**
- 「〜した方が良いかも」「〜も検討してください」
- 「〜という方法もあります」
- 「nit:」「minor:」「optional:」などのプレフィックス
- 「個人的には〜」「好みの問題ですが〜」

**対応:**
- ユーザーに採用可否を確認
- 採用する場合は 🔴 必須修正として扱う
- 採用しない場合は理由を PR にコメント

**例:**
> nit: このメソッド名は `set_xxx` より `update_xxx` の方が意図が明確かもしれません。

---

### ⚪ 情報共有

対応が不要なコメント。認識のみで良い。

**識別パターン:**
- 質問への返信
- 説明の補足
- 「LGTM」「なるほど」「了解しました」
- 議論の途中経過

**対応:**
- 対応不要
- 必要に応じて認識した旨を PR にコメント

**例:**
> 了解しました。その方針で進めてください。

---

## 分類の優先順位

同じコメントが複数のカテゴリに該当する可能性がある場合は、以下の優先順位で分類する:

```
🔴 必須修正 > 🟡 質問 > 🟢 提案 > ⚪ 情報共有
```

**例:**
> この部分は `from_raw()` を使わずに mutation メソッドを使用した方が良いと思いますが、どうでしょうか？

→ 質問形式だが、修正を示唆している → 🟢 提案として分類し、ユーザーに採用判断を仰ぐ

---

## 複合コメントの処理

1つのコメントに複数の指摘が含まれる場合は、それぞれを分解して個別に分類する。

**例:**
> 1. この `unwrap()` は `ok_or()` に変更してください（バグの原因になります）
> 2. あと、変数名は `data` より `response` の方がわかりやすいかも

→ 分解:
- 🔴 必須修正: `unwrap()` → `ok_or()` への変更
- 🟢 提案: 変数名の変更

---

## スレッドの処理

コメントスレッド（返信の連鎖）がある場合:

1. **スレッド全体を読む** - 最新の状態を把握
2. **最終結論を特定** - 議論の結果どうなったか
3. **結論に基づいて分類** - 途中経過ではなく最終結論で判断

**注意:**
- 「解決済み」マークがついていても、修正が必要な場合がある
- レビュアーが「了解」と返信していても、修正の完了を意味しない場合がある
