# ワークフロー詳細

PR レビューコメント対応の各フェーズにおける詳細な実行手順。

---

## Phase 1: コメント取得・分析

### 1.1 コメント取得

`/fetching-pr-review` スキルを使用してコメントを取得する。

```
PR URL: https://github.com/owner/repo/pull/123
```

### 1.2 コメント分類

取得したコメントを以下のカテゴリに分類する。

| カテゴリ | 説明 | 対応アクション |
|---------|------|--------------|
| 🔴 必須修正 | 「〜してください」「〜が必要です」など明確な修正要求 | Phase 4 で修正 |
| 🟡 質問 | 「〜ですか？」「〜について教えてください」など | Phase 2 で回答 |
| 🟢 提案 | 「〜した方が良いかも」「〜も検討してください」など | ユーザーに判断を仰ぐ |
| ⚪ 情報共有 | コメントへの返信、説明の補足など | 対応不要（認識のみ） |

### 1.3 分析結果出力

```markdown
## レビューコメント分析

### 🔴 必須修正 (N件)
| # | ファイル | 行 | 内容 | 対応方針 |
|---|----------|-----|------|---------|
| 1 | path/to/file.rs | 42 | {コメント要約} | {方針} |

### 🟡 質問 (N件)
| # | ファイル | 行 | 質問 |
|---|----------|-----|------|
| 1 | path/to/file.rs | 100 | {質問内容} |

### 🟢 提案 (N件)
| # | ファイル | 行 | 提案内容 | 採用判断 |
|---|----------|-----|---------|---------|
| 1 | path/to/file.rs | 50 | {提案内容} | 👤 ユーザー判断待ち |
```

---

## Phase 2: 質問への回答

🟡 質問カテゴリのコメントに対して回答を作成する。

### 2.1 コードベース調査

質問に答えるために必要な情報をコードベースから収集する。

- 関連ファイルの読み込み
- 既存の実装パターンの確認
- ドキュメント（AGENTS.md, rules/）の参照

### 2.2 回答作成

```markdown
### 質問への回答

#### Q1: {質問内容}

**回答:**
{根拠を示しながら回答}

**参照:**
- `path/to/file.rs:42` - {関連コードの説明}
```

### 2.3 ユーザー確認

回答内容をユーザーに確認し、PR への返信として投稿するか判断を仰ぐ。

---

## Phase 3: 修正方針策定

🔴 必須修正と 🟢 提案（採用決定したもの）について修正方針を策定する。

### 3.1 影響範囲の特定

修正が影響する範囲を調査する。

```markdown
### 影響範囲分析

#### コメント: {コメント内容}

**直接的な修正対象:**
- `path/to/file.rs:42-50`

**波及する修正:**
- `path/to/other.rs` - 同様のパターンが使用されている
- `tests/test_file.rs` - テストの更新が必要

**影響なし:**
- `unrelated/file.rs` - 関連なし
```

### 3.2 修正方針の決定

| 方針タイプ | 説明 |
|-----------|------|
| **局所修正** | 指摘箇所のみを修正 |
| **パターン統一** | 同様のパターンを使用している箇所も一括修正 |
| **リファクタリング** | 根本的な設計変更を伴う修正 |

### 3.3 ユーザー確認

```markdown
## 修正方針確認

以下の方針で修正を進めてよろしいですか？

1. **{コメント1の要約}**
   - 方針: {局所修正 / パターン統一 / リファクタリング}
   - 影響範囲: {ファイル数}件
   - 概要: {修正内容の説明}

2. **{コメント2の要約}**
   ...
```

---

## Phase 4: フェーズ別修正

確定した修正方針に基づき、グループ化して修正を実施する。

### 4.1 修正グループ化

関連する修正をグループ化し、依存関係を考慮した順序で実施する。

```
依存方向: 内側 → 外側
domain → ports → repository → use_case → presentation → tests
```

### 4.2 修正実施

各グループについて以下を実施:

1. **対象ファイルの読み込み** - 現状を把握
2. **修正の適用** - Edit ツールで変更
3. **コンパイル確認** - `cargo check` でエラーがないことを確認
4. **次グループへ** - 依存するコードがあれば次に進む

### 4.3 修正記録

```markdown
## 修正完了

### グループ 1: {グループ名}
- [x] `path/to/file1.rs` - {変更内容}
- [x] `path/to/file2.rs` - {変更内容}

### グループ 2: {グループ名}
...
```

---

## Phase 5: 品質チェック

すべての修正が完了したら品質チェックを実施する。

### 5.1 チェック項目

```bash
# フォーマット
docker compose exec backend cargo fmt -- --check

# Lint
docker compose exec backend cargo clippy --all-targets -- -D warnings

# テスト
docker compose exec backend cargo test
```

### 5.2 問題がある場合

| 問題 | 対応 |
|------|------|
| フォーマット差分 | `cargo fmt` を実行 |
| Clippy 警告 | 警告内容に従い修正 |
| テスト失敗 | 失敗原因を調査し修正 |

### 5.3 品質チェック結果

```markdown
## 品質チェック結果

| チェック | 結果 |
|---------|------|
| cargo fmt | ✅ Pass |
| cargo clippy | ✅ Pass |
| cargo test | ✅ Pass (N tests) |
```

---

## Phase 6: ルール化検討

修正内容から汎用的なルールを抽出できるか検討する。

### 6.1 ルール化の判断基準

[ルール化判断基準](rule-extraction.md) を参照。

### 6.2 ルール候補の抽出

```markdown
## ルール化候補

### 候補 1: {ルール名}

**元のコメント:** {レビューコメント}

**抽象化したルール:**
{コンテキストに依存しない形で記述}

**追加先候補:**
- `.claude/rules/backend/{file}.md` - {理由}

**採用判断:** 👤 ユーザー確認待ち
```

### 6.3 ルールの追加

ユーザーが採用を決定したルールについて:

1. 既存ルールファイルを読み込み
2. 適切なセクションに追加
3. 矛盾する記述がないか確認
4. コミット

---

## 最終コミット

すべての作業が完了したらコミットを作成する。

```markdown
## コミット内容

### 修正コミット
- `{hash}` - {修正内容のサマリー}

### ルール追加コミット（該当時）
- `{hash}` - docs: add {rule name} to {file}
```
